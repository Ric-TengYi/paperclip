# Paperclip 中文优先汉化设计

## 概要

本设计的目标是将 `paperclipai/paperclip` fork 到 `Ric-TengYi/paperclip`，并在 fork 上完成一次面向中文用户的整站汉化。

本次汉化采用“中文优先并保留英文术语”的策略：

- 默认用户可见内容以中文呈现
- 保留关键英文术语、命令、路径、环境变量、API 路径、模型名、adapter 名称
- 不引入完整多语言切换系统
- 不将本次工作扩展为通用 i18n 基础设施改造

## 目标

- fork 上游仓库到 `Ric-TengYi/paperclip`
- 在 fork 的工作分支上完成前端 UI、README、主要 docs、CLI 输出、后端用户可见错误信息的中文化
- 保持项目可运行、可构建、可继续同步上游

## 非目标

- 不实现语言切换器
- 不做中英双语并存 UI
- 不修改数据库字段、API 字段、路由名、命令名、flags、环境变量名
- 不对历史计划文档、测试快照、内部调试日志进行全面翻译
- 不将所有内部开发文档全部翻成中文

## 交付范围

### 1. 仓库层

- 将 `paperclipai/paperclip` fork 到 `Ric-TengYi/paperclip`
- 在 fork 上创建汉化分支
- 将最终代码保留在 fork 的分支中，便于后续继续开发或发 PR

### 2. 前端 UI

覆盖用户直接可见的主要界面文案，包括但不限于：

- 登录 / 注册 / board claim / onboarding
- 导航、首页、dashboard
- company / agent / issue / project / goal / approval / activity / cost 等主要页面
- 常用按钮、状态文本、表单标签、空状态、弹窗提示、错误提示

### 3. 后端用户可见信息

仅翻译会直接返回给前端用户、或者用户会在运行中直接看到的错误与提示，例如：

- 认证失败
- 权限不足
- onboarding / claim / company 创建相关错误
- CLI 以外的 REST 错误信息中面向用户的可见部分

内部调试日志、协议层标识、错误码名不做无差别翻译。

### 4. CLI 输出

翻译这些内容：

- `--help` 说明文本
- onboarding / doctor / configure 等交互提示
- 常见成功 / 失败提示

保留这些内容：

- 命令名
- flags
- 环境变量名
- 路径和示例命令

### 5. 文档

优先翻译用户最常接触的入口和主流程文档：

- `README.md`
- 主要使用说明
- 主要开发 / 部署 / Docker / CLI 指南

不一次性重写所有历史计划、深层设计文档和测试说明。

## 术语策略

统一采用“中文主句 + 英文术语保留”的方式。

推荐术语：

- `Company` -> “公司”
- `Agent` -> “Agent”
- `Issue` -> “任务 / Issue”
- `Project` -> “项目 / Project”
- `Goal` -> “目标 / Goal”
- `Launch` -> “启动 / Launch”
- `OpenClaw Gateway` -> 保留英文
- `Codex` / `Claude Code` / `Cursor` / `Gemini CLI` -> 保留英文
- `heartbeat` -> “心跳 / heartbeat”
- `approval` -> “审批 / approval”

固定不翻译：

- 命令、flags、环境变量、API 路径、数据库字段、adapter type、模型名、文件路径

## 实施方式

### UI

- 高频重复文案优先收拢到少量常量或映射中
- 页面级零散文案按页面就地翻译
- 对于明显高复用文本，顺手做小范围归并，降低后续继续散落的风险

### Server

- 只修改用户会真正看到的错误提示
- 保持内部可观测性和排障信号不被中文化破坏

### CLI

- 以“中文解释 + 英文命令原样保留”为原则
- 保证用户复制文档中的命令后仍然可直接执行

### Docs

- 优先中文化入口型文档和主流程文档
- 保持技术例子、命令块、配置块原样

## 执行顺序

1. 修复本地 GitHub 认证
2. fork 到 `Ric-TengYi/paperclip`
3. 创建汉化工作分支
4. 完成 UI 主流程汉化
5. 完成后端用户可见错误和 CLI 输出汉化
6. 完成 README 和主要 docs 汉化
7. 运行构建与关键验证
8. 输出改动摘要和后续使用说明

## 验证

至少执行以下验证：

- 前端能正常启动
- 核心页面能打开且主要中文文案可见
- 认证、onboarding、company 创建、agent 创建等主流程无明显回归
- `pnpm build` 成功
- 若可行，补充 `pnpm -r typecheck`

如有无法完成的验证项，需明确说明。

## 风险与控制

### 1. 范围膨胀

控制方式：

- 历史计划、深层设计文档、测试快照不纳入本次整站汉化
- 只覆盖实际面向用户的主路径和主文档

### 2. 术语不一致

控制方式：

- 先定义术语策略
- 按统一规则全仓落地

### 3. 改坏逻辑

控制方式：

- 不改协议字段、命令名、flags、环境变量名、数据库字段
- 仅修改显示层文案与用户可见文本

### 4. fork 阻塞

控制方式：

- 优先修复 `gh auth`
- fork 成功后再进行目标仓库写入

## 推荐方案

采用“轻量文案层 + 定向翻译”方案：

- UI 做轻量集中整理，不引入重型 i18n
- docs / CLI / server 错误做定向中文化
- 以可维护、可同步 upstream、可快速交付为第一优先级

## 完成标准

当满足以下条件时视为完成：

- 仓库已成功 fork 到 `Ric-TengYi/paperclip`
- fork 分支上已有整站中文化改动
- UI 主路径、主要文档、CLI 输出、用户可见错误已完成中文化
- 构建或类型检查通过，或明确说明未通过项及原因
- 提供最终分支信息与后续使用说明
